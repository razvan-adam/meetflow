# Coding conventions

How code is written in MeetFlow, so the codebase stays consistent as features are added. Decided in MF-34. Where a tool enforces a rule, the tool wins; this document explains the rest.

## Formatting and checks

Nobody formats by hand or argues about style: the formatters decide, and CI fails on unformatted code.

| Area | Tool | Fix locally | Checked in CI |
|---|---|---|---|
| Backend formatting (Java, `pom.xml`, config files) | Spotless with Palantir Java Format for Java (4 spaces, 120 columns) and SortPom for `pom.xml` (2 spaces) | `./mvnw spotless:apply` | `./mvnw spotless:check` |
| Backend bugs and null-safety | Error Prone and NullAway, inside the Java compiler | Fix the compile error | Every compile |
| Frontend formatting | Prettier (no semicolons, single quotes, 100 columns) | `npm run format` | `npm run format:check` |
| Frontend lint | oxlint | Fix the reported rule | `npm run lint` |

- Run the formatter before committing. Install the Palantir Java Format and Prettier plugins in your editor to format on save; `.editorconfig` sets the basics for every editor.
- Line endings are LF everywhere, enforced by `.gitattributes`; only Windows `.cmd` files use CRLF.
- Flyway migrations are not formatted by Spotless: changing an applied migration, even its whitespace, changes its checksum.
- Don't silence a check to get a build through. If a rule is wrong for us, turn it off in the config with a comment saying why.

## Backend

### Package structure

- One package per Spring Modulith module under `com.meetflow` (`identity`, `teams`, `meetings`, `tasks`, `minutes`, `notifications`); see `docs/architecture.md`.
- A module starts as one flat package. Classes are **package-private by default**; only the module's API for other modules is `public`. Add subpackages only when a module grows, remembering that Modulith treats subpackages as internal.
- Modules talk through another module's public API or through application events. Use events for side effects that the publisher shouldn't depend on (e.g. a closed meeting triggers minutes and emails). `ModularityTests` fails on boundary violations.

### Naming

| Kind | Name | Example |
|---|---|---|
| Entity | Domain noun, no suffix | `Meeting`, `Task` |
| Repository | `<Entity>Repository` | `TaskRepository` |
| Service (business logic) | `<Concept>Service` | `TaskService` |
| REST controller | `<Resource>Controller` | `MeetingController` |
| Request / response body | `<Action or resource>Request` / `<Resource>Response` | `CreateTaskRequest`, `TaskResponse` |
| Event | Past tense, `<What happened>Event` | `MeetingClosedEvent` |
| Configuration | `<Area>Config` | `SecurityConfig` |
| Test class | `<Class or area>Tests` | `TaskServiceTests` |

Names use the domain words from `AGENTS.md` and `docs/core-flow.md` (meeting series, agenda item, decision, task, minutes), not synonyms.

### Java style

- Constructor injection only, with `final` fields; no `@Autowired` on fields or setters in production code (tests may use field injection).
- Records for request, response and event types. Entities never leave the module's controller layer: map them to response records.
- `Optional` only as a return type, never for fields or parameters.
- No Lombok: records and modern Java cover what it would give us, and it hooks into the compiler.
- **Null-safety:** every package is `@NullMarked` (JSpecify), so types are non-null unless marked `@Nullable`, and NullAway fails the build on unsafe use. A new package needs a `package-info.java` with `@NullMarked`.
- Comments explain *why*, not *what*. Every module's `package-info.java` describes what the module owns.
- Never log meeting content or personal data beyond IDs (GDPR; see `docs/architecture.md`).

### Database

- Schema changes go in a new Flyway migration, `V<n>__<module>_<what>.sql`; never edit an applied one.
- Tables and columns are `snake_case`, tables singular (`meeting`, `agenda_item`). IDs are UUIDs generated by the application; timestamps are `timestamptz` in UTC. See `docs/data-model.md`.

## API style

- REST + JSON, all under `/api`. Resource names are plural nouns in kebab-case (`/api/agenda-items`).
- Lists and creation are nested under the parent that scopes them: `GET /api/teams/{teamId}/meetings`, `POST /api/meetings/{meetingId}/tasks`. A single resource has a flat URL: `GET /api/tasks/{taskId}`.
- Team access is checked on the server for every request, whatever the URL contains. A resource the user can't access answers **404**, so its existence isn't revealed.
- JSON fields are `camelCase`. Timestamps are ISO-8601 in UTC (`2026-10-29T14:00:00Z`); dates are `YYYY-MM-DD` (task deadlines). IDs are UUID strings.
- Status codes: `200` read or update, `201` created (with the new resource in the body), `204` no body, `400` validation error, `401` not logged in, `403` logged in but not allowed by role (e.g. not the organizer), `404` not found or no access, `409` conflict (e.g. a concurrent edit caught by optimistic locking).
- Errors use RFC 9457 Problem Details (`application/problem+json`, Spring's `ProblemDetail`). Validation errors list the invalid fields.
- No version in the URL: the frontend and backend are deployed together. Revisit if outside clients use the API.

## Frontend

- One component per file, named in `PascalCase` like the file (`HomePage.tsx`). Hooks start with `use`; other files are `camelCase` (`client.ts`).
- Screens go in `src/pages`, shared providers and routing in `src/app`, API calls in `src/api`.
- All server calls go through `apiFetch` and TanStack Query hooks in `src/api` (one file per resource); components don't call `fetch` directly.
- Styles use CSS modules (`Component.module.css`) and the tokens in `src/styles`; colors and type follow `docs/visual-style.md`.

## Tests

- Every behavior change comes with tests. Test method names describe the behavior: `carriesOpenTasksToNextMeeting`, not `testCarryOver`.
- Backend, from fastest to slowest; use the narrowest that covers the behavior:
  - Plain unit tests for logic without Spring.
  - `@WebMvcTest` for controllers: request and response shape, validation, status codes, and access by a non-member of the team.
  - `@ApplicationModuleTest` for a module's logic with its repositories, against PostgreSQL via Testcontainers.
  - `@SpringBootTest` only for checks that need the whole app. Each different test setup starts another Spring context, which slows the build.
- Frontend: test files sit next to the code (`HomePage.test.tsx`). Use React Testing Library queries by role or label, as a user would find things, not CSS selectors or test IDs.

## Commits, branches and pull requests

- **Branches:** `<type>/<short-purpose>` in kebab-case, without the ticket key, e.g. `feature/team-invitations`, `fix/session-timeout`. Types: `feature`, `fix`, `chore`, `docs`.
- **Commits:** start with the Jira key, then an imperative summary in sentence case, e.g. `MF-34 Add the coding conventions and backend checks`. Commits without a ticket leave the key out. Keep the summary under about 72 characters; add a body when the reason isn't obvious.
- **Pull requests:** one ticket per PR, kept small. The PR title follows the commit format. `main` is protected: a PR and passing `Frontend` and `Backend` checks are required to merge, and PRs are merged with a merge commit.
- Never commit secrets or `.env` files (see `backend/.env.example`).
